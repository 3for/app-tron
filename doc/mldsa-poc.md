# ML-DSA-44 random-key proof of concept

This build variant demonstrates that app-tron can generate an ML-DSA-44 key,
sign a TRON transaction ID, and produce a signature accepted by java-tron. It
is deliberately not a production account implementation.

## Scope and security boundary

- Enable it explicitly with `MLDSA_POC=1`; normal builds contain no PQ APDUs or
  ML-DSA implementation.
- The key is randomly generated by `MLDSA_keygen()` and retained only in the
  app heap. Exiting/restarting the app, aborting the session, or a fatal crypto
  error erases it. It cannot be recovered from the Ledger seed.
- One key can sign multiple transactions during the same uninterrupted app
  session. ML-DSA signatures are randomized, so two valid signatures made by
  the same key over the same transaction ID need not be equal.
- `INS_GENERATE_PQ_KEY` supports an explicit on-device address confirmation
  mode (`P1=1`). Hardware workflows must use it before funding the temporary
  account; `P1=0` remains only for automated PoC probes.
- `INS_SIGN_PQ` currently accepts only `TransferContract`, owner permission 0,
  where `owner_address` exactly matches the address derived from the active PQ
  public key. Legacy signing, GCS, TIP-712, swap, and other PQ contract types
  are intentionally rejected while a PQ key is resident.
- The message is exactly `SHA256(transaction.raw_data)`, using pure ML-DSA-44
  with an empty context. There is no second hash or pre-hash ML-DSA mode.
- The address is `0x41 || Keccak256(public_key)[12..31]`, where `public_key` is
  the complete 1312-byte FIPS-204 public-key encoding.
- The implementation is linked from API-26 `lib_cxng`; this PoC does not claim
  a production side-channel, constant-time, recovery, or firmware-security
  posture. Those require a separate Ledger security review and real-device
  measurements.

## APDU protocol

All integers are unsigned big-endian. The SDK enum `MLDSA_44 = 0` is internal
and must not be confused with TRON's wire-level `PQScheme.ML_DSA_44 = 2`.

| INS | Name | Request | Response |
| --- | --- | --- | --- |
| `0x30` | capabilities | empty | version, scheme, pk size, sig size, flags |
| `0x32` | generate key | `P1=0` probe or `P1=1` confirmed hardware flow, `P2=2` | session metadata after optional approval |
| `0x34` | sign raw data | first payload is `session_id || raw_data`; continuation payloads are raw data | asynchronous review, then session metadata |
| `0x36` | read result | `session_id[4] || object[1] || offset[2] || requested[1]` | chunk header and bytes |
| `0x3A` | abort session | `session_id[4]` | status only; key is erased |
| `0x3C` | self-test | empty | keygen/sign/device-verify metadata |
| `0x3E` | close result | `session_id[4]` | status only; signature is erased, key remains |

Result objects are public key `1`, signature `2`, and self-test message `3`.
Chunks contain at most 220 bytes. Session metadata is:

```text
version[1] || scheme[1] || session_id[4] || address[21] ||
public_key_size[2] || signature_size[2] || SHA256(public_key)[32]
```

`signature_size` is zero after key generation and 2420 after signing.

## Error and cleanup semantics

A malformed, oversized, unsupported, or owner-mismatched transaction clears
the transaction parser, raw-data buffer, hash, UI data, and any old result, but
returns to `PQ_KEY_READY` with the same key. User rejection follows the same
recoverable path. A keygen/sign/device-verify failure and the ordinary global
app reset erase the private key and return to `IDLE`.

This split is intentional: ordinary `send_sign_status()` and
`reset_app_context()` cannot be used for recoverable PQ transaction errors,
because the global reset owns the fatal session cleanup.

## Speculos probe

Start Speculos in the pinned Linux builder after building:

```sh
docker run --rm -p 5000:5000 -p 9999:9999 \
  -v "$PWD:/app" -w /app \
  ghcr.io/ledgerhq/ledger-app-builder/ledger-app-dev-tools@sha256:1350bb805ce3f03a7cdf403de701c5e6aa5246c94fa251660f88949bea3c8638 \
  speculos --model nanosp --api-port 5000 --apdu-port 9999 \
  --display headless /app/bin/app.elf
```

In another shell:

```sh
python3 tests/pq_poc_probe.py --output-dir /tmp/tron-mldsa-poc
```

The probe first injects a malformed transaction and checks that the public-key
fingerprint is unchanged. It then approves a native TRX transfer, retrieves the
1312-byte public key and 2420-byte signature, and writes `raw_data.bin`,
`message_hash.bin`, `public_key.bin`, and `signature.bin`. The message passed to
java-tron's `MLDSA44.verify` is `message_hash.bin`, not `raw_data.bin`.

The Ragger equivalents are in `tests/ragger/test_mldsa_poc.py`. They skip on a
normal build where the experimental capability APDU is absent.

The independent java-tron verifier sources and compilation instructions live
in `tron-pq-verify/`.

## Real device, Nile, and private-chain broadcast

`tests/pq_hardware_nile.py` is the host-side real-device driver. It confirms
the temporary PQ address, obtains a node-built `raw_data`, drives chunked
signing, verifies the artifacts with `tron-pq-verify`, encodes `PQAuthSig`, and
optionally broadcasts through `/wallet/broadcasthex`.

Install `tests/ragger/requirements.txt`, connect and unlock the device, sideload
the matching API-26 `MLDSA_POC=1` build, and open the Tron app before running
the hardware flow. Do not pass the Speculos-only transport options for a real
device.

Check a network without opening the device:

```sh
python3 tests/pq_hardware_nile.py --check-chain
```

Broadcasting has a redundant hard gate: `--broadcast` is rejected before key
generation unless `getAllowMlDsa44` is exactly 1, and the parameter is checked
again immediately before the network call. A missing `value` in java-tron's
JSON response is protobuf default zero. Consequently, public Nile can be used
for a local signing/verification dry run, but cannot receive a PQ broadcast
while its ML-DSA parameter remains disabled. Do not fund an ephemeral PQ
address on such a network.

The reproducible one-node test network and full broadcast procedure are in
`tests/private-chain/README.md`.

## Verified result

The Nano S+ API-26 Speculos flow completed key generation, recoverable parser
failure, transaction review, signing, device-side verification, and chunked
retrieval. The exported artifacts were independently checked against the
java-tron workspace implementation:

```text
pk=1312 message=32 signature=2420 valid=true
```

All devices declared in `ledger_app.toml` compile with the pinned API-26 SDK.
The resulting ELF section sizes were:

| Target | text | data | bss |
| --- | ---: | ---: | ---: |
| Nano S+ | 148044 | 0 | 40960 |
| Nano X | 147772 | 0 | 28672 |
| Stax | 172687 | 0 | 36864 |
| Flex | 172937 | 0 | 36864 |
| Apex P | 169111 | 0 | 40960 |

These are build/link results, not runtime memory or watchdog measurements.

Remaining production gates are deterministic cross-wallet key derivation and
recovery, real-device stack/heap/time/watchdog measurements (with Nano X as a
minimum gate), production host integration, broader contract policy, and
Ledger security review. A PoC-only host flow and private-chain broadcast are
now covered; they do not satisfy those production gates.
